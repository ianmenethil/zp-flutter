# docker — Container Images for the Example App

Two independent Docker setups for the same two-app example (`example/backend` +
`example/app` built for web): `docker/local/` runs the full stack on your machine via
Docker Compose; `docker/cloudflare/` builds the images Cloudflare Workers Containers
deploys in production. Neither is used to package `zenpay_dart`, `zenpay_flutter`, or
`zenpay_embedded` themselves — those packages are only consumed as source inside these
images.

Don't invoke `docker`/`docker compose` directly — use `dart run cli.dart --docker-build`
/ `--docker-run` / `--docker-rebuild` from the repo root; the Compose file's build context
(`../..`, i.e. the repo root) only resolves correctly when invoked the way `cli.dart`
invokes it. `--docker-build` only checks Docker Compose v2 is available — it just builds
images, nothing else needs to exist yet. `--docker-run` and `--docker-rebuild` (which
calls `--docker-build` then `--docker-run`) additionally require the TLS cert and the
service-account file below before they'll start.

## `docker/local/` — local Compose stack

- **[docker-compose.yml](local/docker-compose.yml)** — two services, `backend` (`:7000`)
  and `frontend` (`:8080`), on a shared bridge network. `frontend` depends on `backend`.
- **[Dockerfile.backend](local/Dockerfile.backend)** / **[Dockerfile.frontend](local/Dockerfile.frontend)**
  — multi-stage builds. Each `COPY`s only the source it needs (backend: `zenpay_dart/` +
  `example/backend/`; frontend: `zenpay_dart/`, `zenpay_flutter/`, `zenpay_embedded/` +
  `example/app/`) into a throwaway image-local `pubspec.yaml` with its own `workspace:`
  list, rather than reusing the repo's real root `pubspec.yaml` — pulling that in would
  require every workspace member on disk, defeating the point of copying only what's
  needed. **If the real root workspace's member list changes, update these two
  hand-written `workspace:` lists too** (and their `docker/cloudflare/` counterparts,
  which are identical) — nothing keeps them in sync automatically.
- The `frontend` service requires HTTPS: the SDK's checkout return URI must be `https`
  (see `cli.dart`'s `_requireDockerTlsCert`), so nginx is configured with TLS using certs
  bind-mounted from `example/app/localhost+2*.pem`. Those certs come from `mkcert` —
  either already generated by `dart run cli.dart --bootstrap`, or generated on the spot by
  `--docker-run`/`--docker-rebuild` themselves if missing and `mkcert` is on `PATH`
  (`_requireDockerTlsCert` in `cli.dart`). Compose itself does not generate them.
- reCAPTCHA Enterprise (`recaptcha_verifier.dart`) is entirely `.env`-driven, same as
  native: `RECAPTCHA_SERVICE_ACCOUNT_JSON` accepts inline JSON or a file path, and the
  `backend` service loads `example/backend/.env` via `env_file:` — no bind mount, no
  file required. `config.dart`'s `recaptchaConfigurationErrors` (checked at startup in
  both native and Docker, since both run the same `bin/server.dart`) enforces that
  `RECAPTCHA_PROJECT_NUMBER` / `RECAPTCHA_SERVICE_ACCOUNT_JSON` / `RECAPTCHA_SITE_KEY_WEB`
  are either all three set or all three empty — refusing to start rather than silently
  leaving the client widget rendering with server-side enforcement off.
- Both Dockerfiles pin nginx's `worker_processes` to `1`. nginx's default `auto` spawns one
  worker per host-visible CPU core; under a constrained/virtualized environment the
  container can see far more cores than it's actually allocated, exhausting its memory
  budget on startup.

## `docker/cloudflare/` — production Container images

- **[Dockerfile.backend](cloudflare/Dockerfile.backend)** / **[Dockerfile.frontend](cloudflare/Dockerfile.frontend)**
  — same build shape as `docker/local/`, referenced directly from `wrangler.jsonc`'s
  `containers[].image` as the build source for `--cf-deploy` (`npm run cf:deploy`). Not
  run locally.
- No TLS setup in `Dockerfile.frontend`: Cloudflare's edge terminates HTTPS on the public
  `*.workers.dev`/custom domain, so this container serves plain HTTP on `:8080`. (This is
  one of several differences from `docker/local/Dockerfile.frontend` — don't merge the two.)
- `Dockerfile.frontend` takes an extra `BACKEND_BASE_URL` build arg (passed through as a
  `--dart-define`) that `docker/local/Dockerfile.frontend` doesn't have — the local build
  only passes `APP_RETURN_URI_WEB`. Production's frontend needs to know its backend's URL
  explicitly since the two aren't reachable via `localhost` the way the local Compose
  network makes them.
- `Dockerfile.frontend` replaces nginx's default `access.log`/`error.log` symlinks (which
  normally point at `/dev/stdout`/`/dev/stderr`) with real files. Cloudflare's Firecracker
  container runtime fails to `open()` those device symlinks (`ENXIO`), which is fatal for
  nginx's `error_log` directive at startup — before it even parses the rest of the config.

## Verification

No tests here — these are Dockerfiles and a Compose file, not Dart source. Verify by
building: `dart run cli.dart --docker-build`, then `dart run cli.dart --docker-run` and
confirm both containers report healthy on `:7000`/`:8080`.
