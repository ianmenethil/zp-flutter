# zenpay_flutter

Client-side Flutter SDK for orchestrating ZenPay Hosted Checkout sessions across Android, iOS, and Web.

Presents the checkout URL generated by a merchant backend in a platform-native browser surface (Android Custom Tabs, iOS `SFSafariViewController`, or a new tab on Web), watches for dismissal or timeout, intercepts the return deep link, and settles with a strongly-typed outcome. Holds no credentials, makes no network calls, and writes no logs of its own.

## Source Guide

### Public Entrypoints

- **[lib/zenpay_checkout.dart](lib/zenpay_checkout.dart)**: Barrel export for the public API — `ZpCheckout`, `ZpCheckoutConfiguration`, `ZpCheckoutOutcome` and its variants, `ZpCheckoutException` hierarchy, `ZpCheckoutEvent`/`ZpCheckoutObserver`, `isAllowedCheckoutUrl`, `CheckoutPresenter`, `ZpReturnUriSource`, and the web return-popup helper. Deliberately exports only `isAllowedCheckoutUrl` from the validator file, not the validator class itself, so an external presentation surface can apply the same host/scheme policy without a second copy to drift.
- **[lib/testing.dart](lib/testing.dart)**: Separate entrypoint (`package:zenpay_flutter/testing.dart`) exporting `FakeReturnUriSource`, a `ZpReturnUriSource` a test drives directly via `emit()` instead of through App Links or a browser — kept out of the production barrel so test doubles never ship to app code.

### `lib/src/checkout/` — orchestration

- **[run_checkout_flow.dart](lib/src/checkout/run_checkout_flow.dart)**: Implements `ZpCheckout`, the controller. `reserveLaunch()`/`releaseLaunchReservation()` guard the web user-gesture window; `open()` validates the URL, races the return-URI stream against presenter dismissal and a configured timeout, and resolves exactly once with a `ZpCheckoutOutcome`; `dispose()` settles any in-flight checkout as dismissed. One checkout may be active per instance — a second `open()` throws `ZpCheckoutAlreadyActiveException`. Also defines `mapLaunchFailureCode`, translating a `url_launcher` throw into a `ZpLaunchFailureCode`.
- **[track_active_checkout.dart](lib/src/checkout/track_active_checkout.dart)**: Internal `ActiveCheckout` — the state for one in-flight launch. `expireAfter` arms the timeout timer; `finish` is first-call-wins and tears down the timer plus every watched stream subscription, so a timeout firing just after a genuine return can't double-settle the outcome.
- **[validate_checkout_url.dart](lib/src/checkout/validate_checkout_url.dart)**: `isAllowedCheckoutUrl` — the HTTPS-only, credential-free, fragment-free, length-bounded, host-allowlisted predicate a checkout URL must pass before a browser opens. `ZpLaunchValidator` wraps it, throwing `ZpInvalidLaunchException` on failure.

### `lib/src/configuration/` — settings

- **[checkout_settings.dart](lib/src/configuration/checkout_settings.dart)**: `ZpCheckoutConfiguration` — the immutable policy passed to `ZpCheckout`: allowlisted hosts, the expected HTTPS return URI, the presentation timeout, browser UI toggles, return-URI/value length bounds, and an optional `ZpCheckoutObserver`. Constructor assertions validate every invariant (non-empty hosts, a clean HTTPS return URI, a positive timeout, sane length floors) at instantiation time rather than at use.

### `lib/src/exceptions/` — errors

- **[checkout_errors.dart](lib/src/exceptions/checkout_errors.dart)**: Sealed `ZpCheckoutException` hierarchy callers can catch as one type — `ZpCheckoutAlreadyActiveException` (a second checkout started while one is active), `ZpCheckoutDisposedException` (called after `dispose()`), `ZpInvalidLaunchException` (the checkout URL failed `isAllowedCheckoutUrl`).

### `lib/src/models/` — outcomes

- **[checkout_results.dart](lib/src/models/checkout_results.dart)**: Sealed `ZpCheckoutOutcome` — exactly one of `ZpReturnReceived` (a validated return URI arrived), `ZpPresentationDismissed` (browser closed with no return), `ZpTimedOut` (the configured timeout elapsed), or `ZpLaunchFailed` (the browser never opened, carrying a `ZpLaunchFailureCode`) settles every `ZpCheckout.open` call. None of them is proof of payment — that's the merchant backend's signed webhook, always.

### `lib/src/observability/` — telemetry

- **[checkout_telemetry.dart](lib/src/observability/checkout_telemetry.dart)**: `ZpCheckoutObserver` (with a `.from` factory over a plain callback) and the sealed `ZpCheckoutEvent` hierarchy it receives — `ZpLaunchRejectedEvent`, `ZpPresentedEvent`, `ZpReturnRejectedEvent` (carrying a `ZpReturnRejectionReason`), `ZpReturnAcceptedEvent`, `ZpFinishedEvent`. Events never carry a full checkout URL or raw return query, so forwarding one to a log sink can't leak credentials. An exception thrown from `onEvent` is caught and discarded — an observer can never change a checkout's outcome.

### `lib/src/presentation/` — platform browser surfaces

- **[open_checkout_contract.dart](lib/src/presentation/open_checkout_contract.dart)**: Abstract `CheckoutPresenter` — `openCheckout`, `dismissCheckout`, `events`, and the `reserveLaunch`/`releaseReservation` pair (no-op by default; only Web overrides them). `PresentationLaunchResult` reports whether a launch succeeded and whether it fell back to the external browser.
- **[open_checkout_pick_platform.dart](lib/src/presentation/open_checkout_pick_platform.dart)**: Conditional-import resolver — `createCheckoutPresenter()` picks the Web or Mobile implementation at compile time via `dart.library.js_interop`.
- **[open_checkout_on_mobile.dart](lib/src/presentation/open_checkout_on_mobile.dart)**: Mobile `CheckoutPresenter` over `url_launcher`'s `LaunchMode.inAppBrowserView` (Custom Tabs on Android, `SFSafariViewController` on iOS), falling back to the external browser when allowed. `url_launcher` exposes no dismissal callback for either surface, so dismissal is inferred from an app-resume lifecycle event after a short fixed grace period (long enough for a genuine deep-link return to win the race first) — see the file's doc comment for why, including the upstream platform issues this works around. Programmatic `dismissCheckout()` only works on iOS; Android Custom Tabs has no OS-level close.
- **[open_checkout_on_web.dart](lib/src/presentation/open_checkout_on_web.dart)**: Web `CheckoutPresenter` over `dart:js_interop`'s `window.open`. `reserveLaunch()` opens a blank popup synchronously inside the caller's tap handler, before any `await` can end the browser's user-gesture window; `openCheckout()` then navigates that already-open window instead of calling `window.open` again. Dismissal is detected by polling `window.closed` — the platform gives no close event for a window this app opened.

### `lib/src/return_handling/` — return-URI ingestion and validation

Two problems, not nine independent files: (1) mobile and web need different mechanisms to detect that a return happened, behind one shared `ZpReturnUriSource` contract; (2) web-only, checkout opens in a second browser tab, so that tab has to relay its landing back to the tab that opened it.

- **[listen_for_return_contract.dart](lib/src/return_handling/listen_for_return_contract.dart)**: Abstract `ZpReturnUriSource` — a `Stream<Uri>` of incoming returns, replaying any cold-start link first.
- **[listen_for_return_pick_platform.dart](lib/src/return_handling/listen_for_return_pick_platform.dart)**: Conditional-import resolver — `createDefaultReturnUriSource()` picks the Mobile (`app_links`) or Web (popup listener) implementation at compile time.
- **[validate_return_url.dart](lib/src/return_handling/validate_return_url.dart)**: `ZpReturnValidator` — checks a candidate return URI's length, exact scheme/host/port/path match against `expectedReturnUri` (via the shared `matchesReturnUriAddress` predicate), and parses+bounds its query, rejecting a repeated key or an over-length value. Returns the normalized URI or `null`, reporting *why* via a `ZpReturnRejectionReason` callback without ever including the candidate URI itself.
- **[mobile/listen_for_return_on_mobile.dart](lib/src/return_handling/mobile/listen_for_return_on_mobile.dart)**: `AppLinksReturnUriSource`, wrapping `package:app_links` behind `AppLinksPlatformAdapter` for testability. Combines the cold-start initial link with the runtime stream; the initial-link read is guarded by a process-wide static flag (not an instance field), because `app_links`' `getInitialLink()` keeps returning the same cached value for the life of the process and a second, unrelated checkout must not replay it.
- **[web/listen_for_return_on_web.dart](lib/src/return_handling/web/listen_for_return_on_web.dart)**: `WebPopupReturnUriSource` — listens for the `postMessage` handoff described below and turns it into a `ZpReturnUriSource`, trusting only same-origin messages.
- **[web/web_popup_sends_url_back.dart](lib/src/return_handling/web/web_popup_sends_url_back.dart)**: `completeWebCheckoutReturnIfPopup()` (Web implementation) — called as the first line of `main()`; if this page is a same-origin popup that has navigated to the expected return address, relays the URL to `window.opener` via `postMessage` and closes the window.
- **[web/web_popup_not_used_on_mobile.dart](lib/src/return_handling/web/web_popup_not_used_on_mobile.dart)**: Mobile stand-in for the file above — always returns `false`, since the popup handoff is a Web-only concept.
- **[web/web_popup_pick_platform.dart](lib/src/return_handling/web/web_popup_pick_platform.dart)**: Conditional-import resolver exposing `completeWebCheckoutReturnIfPopup()` at the barrel-export level.
- **[web/web_return_protocol.dart](lib/src/return_handling/web/web_return_protocol.dart)**: The `postMessage` payload format (`encodeZpReturnMessage`/`decodeZpReturnMessage`) plus origin/address checks (`parseIncomingReturnMessage`, `matchesReturnAddress`), kept free of `dart:js_interop` on purpose — that import is unavailable under the plain `flutter test` VM platform, and this file's origin-checking logic needs to be unit-testable there.

## Core System Invariants & Rules

1. **Security & Scope Boundaries** — no cryptography, hashing, secret storage, or network calls happen in this package. Checkout URL construction and signing belong on the merchant backend (`zenpay_dart`). `ZpReturnReceived` is a provisional, device-side signal only; final status always comes from the backend's verified webhook.
2. **Web user gesture** — `window.open` only succeeds inside an unbroken user gesture. Applications must call `checkout.reserveLaunch()` synchronously as the very first step of the tap handler, before requesting a checkout URL from the backend, and call `checkout.releaseLaunchReservation()` if that request fails.
3. **Web return popup routing** — Flutter web apps must call `completeWebCheckoutReturnIfPopup(expectedReturnUri: ...)` as the first line of `main()`, and return immediately (skip `runApp`) when it returns `true`.
4. **Mobile dismissal is inferred, not delivered** — Android Custom Tabs and `url_launcher` provide no native dismissal callback; see `open_checkout_on_mobile.dart` for the resume-plus-grace-period workaround and its rationale.
5. **Telemetry is opt-in and isolated** — the SDK produces no logs or analytics on its own; observing happens only through a supplied `ZpCheckoutObserver`, and an observer's own exceptions never affect the checkout.
6. **Strict Dart/Flutter standards** — `strict-casts`, `strict-inference`, `strict-raw-types` (see [analysis_options.yaml](analysis_options.yaml)); every exported public API carries a doc comment; models and configuration are immutable with value equality.
