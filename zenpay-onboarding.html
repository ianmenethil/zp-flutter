Hosted Checkout · Dart & Flutter

Three packages
and one reference.

Two SDKs make a ZenPay integration, a third is an opt-in presentation swap, and a runnable example wires all of it together. This guide takes them in that order — what each package is for, then how to run the reference.

Overview

How the four pieces fit

A merchant integration is zenpay_dart on your server and zenpay_flutter in your app. Everything else is optional or illustrative.

zenpay_dart required

Pure-Dart backend SDK. Fingerprints, launch URLs, callback verification, callback URL tokens. Server-side only.

zenpay_flutter required

Flutter client SDK. Presents checkout, detects the return, settles one typed outcome. Complete on its own.

zenpay_embedded opt-in

An in-app WebView presenter implementing the same contract. Never the default; adds a webview_flutter dependency only if imported.

example/ reference

A Shelf backend and Flutter app demonstrating the full flow. Merchants copy the pattern, not the package.

01Backend SDK · server-side only

zenpay_dart

Pure Dart, no Flutter. It builds the signed URL that launches checkout and verifies the webhook that reports the result. It makes no outbound network calls — the launch URL is computed entirely offline.

Never import this from a Flutter app

It handles the merchant password and the HMAC secret. In a Flutter package those ship to every customer device. Your app talks to your backend over HTTP and never to ZenPay directly.

The five calls that carry an integration

Everything else in the package supports these. The first two happen when you prepare an attempt, the middle two when you hand a URL to a client, the last when ZenPay reports back.

CallWhat it does
createZpMupid()
createZpTimestamp()		Mint the merchant-unique payment id (22-char base64url) and the UTC timestamp. Mint both once and carry them forward, so re-exchanging a capability rebuilds the same attempt rather than a new one.
createZpFingerprint(...)SHA3-512 over a pipe-delimited string of credentials plus order fields. Returns ZpFingerprintSuccess or ZpFingerprintFailure. Pass the amount through as-is — the SDK's own per-mode rules already decide what gets hashed.
createZpCallbackUrlToken(...)Mints the signed t token that travels on the return URL, carrying the MUPID as a signed claim. This is what lets a status lookup authorise itself without trusting a caller-supplied id.
createZpCheckoutUrl(...)Assembles and validates the Authorise URL with single-pass percent-encoding. Returns ZpUrlSuccess or ZpUrlFailure.
verifyZpCallback(...)The only call that establishes payment status. Recomputes the expected ValidationCode and compares it in constant time. Returns ZpCallbackVerified, ZpCallbackMalformed, or ZpCallbackRejected — never throws on bad input, because callback bodies are attacker-reachable.

ZpCallbackVerified carries no data

It is pass/fail only, mirroring the TypeScript SDK. You already hold the body you passed in — read the fields you need off it once authenticity is proven, using ZpPluginMode.callbackReferenceField to find the right reference field for the mode.

Also exported: verifyZpCallbackUrlToken, the pre-flight validators validateZpCheckoutUrlRequest, validateZpFingerprintRequest and validateZpCallbackBody, the typed wrappers ZpCents, ZpMupid and ZpTimestamp, plus createSha3_512, isValidZpTimestamp, resolveZpHashAmountField and zpAmountToCents. Internal defaults and constants are deliberately not exported.

Transaction modes and status codes

WireModeCharges?AmountCallback field
0makePaymentyesrequired, positivepaymentReference

3preauthorizationyesrequired, positivepreauthReference

Pick from the product: a set price is 0, storing a card is 1, a customer-entered amount is 2, holding funds is 3.

Payment status wire codes: 0 pending · 1 error · 3 successful · 4 failed · 5 cancelled · 6 suppressed · 7 in progress. Only 3 is success — both isZpPaymentSuccessful(status) and ZpPaymentStatus.isSuccessful mean exactly == 3. Never treat "not failed" as paid.

What is secret, and what only looks secret

Masking public values adds no security — the customer's own browser receives the same URL — and makes logs impossible to correlate. These are safe to log in full, including inside a complete launch URL:

ValueWhy it is public
__ApiKeyTravels in the Authorise URL the customer's browser loads.
__FingerprintA per-transaction SHA3-512 digest, also in that URL. Useless without the password that produced it.
merchantCodeA merchant identifier in the URL path.
merchantUniquePaymentIdAn ordinary opaque per-payment reference.
timestamp, customerReference, paymentAmountOrdinary request fields in the URL.
Never log

The merchant password, the HMAC secret passed to createZpCallbackUrlToken, and any cardholder data. The first two are hash inputs only and never appear in any URL this package builds.

02Client SDK · required

zenpay_flutter

Takes the checkout URL your backend built, presents it in a platform-native browser surface, watches the session, intercepts the return, and settles exactly one typed outcome. On its own this is a complete, production-ready integration.

The barrel exports ZpCheckout, ZpCheckoutConfiguration, ZpCheckoutOutcome, ZpCheckoutException, ZpCheckoutEvent, ZpCheckoutObserver, isAllowedCheckoutUrl, CheckoutPresenter, ZpReturnUriSource and the web return helpers. A separate testing.dart entrypoint exports FakeReturnUriSource for deterministic tests without OS platform channels.

Launching checkout

Construct ZpCheckout once in initState and dispose it — one instance per screen, not one per tap. It enforces single-session concurrency and owns the return subscription.

dart · construction
_checkout = ZpCheckout(
  configuration: ZpCheckoutConfiguration(
    allowedCheckoutHosts: allowedCheckoutHosts,
    expectedReturnUri: appReturnUri,
    observer: ZpCheckoutObserver.from((e) => debugPrint('[ZpCheckout] $e')),
  ),
  returnUriSource: createDefaultReturnUriSource(),
);

That debugPrint is your code, not the SDK's

zenpay_dart, zenpay_flutter and zenpay_embedded ship zero print, debugPrint or log calls in their lib/ trees — observer is a plain callback you supply, and it only runs what you write. Emitted events already omit tokens, raw query parameters and full checkout URLs, so logging them is safe by default.

expectedReturnUri is compared exactly — scheme, host, port and path. A mismatch is rejected rather than ignored, and surfaces as an unexplained timeout with nothing in the logs to explain it.

The pay handler has a required ordering

dart · ordering is load-bearing
Future<void> _pay() async {
  if (!_valid()) return;                       // 1. validate synchronously

  if (!_checkout.reserveLaunch()) {            // 2. BEFORE the first await
    _show('Popup blocked'); return;
  }

  try {
    final token = await prepareCheckout(...);  // 3. now async is safe
    final ex = await exchangeCheckout(...);
    await _resolve(await _checkout.open(checkoutUrl: Uri.parse(ex.checkoutUrl)));
  } on Object catch (e) {
    _checkout.releaseLaunchReservation();      // 4. or a blank tab leaks
    _show('Checkout failed');
  }
}
Why

On web, Chrome and Safari only let window.open() succeed when it runs synchronously, directly inside the click — not after an await. This flow has to await your backend before it even has a checkout URL to open, which would normally get the tab blocked as a pop-up. reserveLaunch() works around that by opening a blank tab immediately, before the first await; open() then just navigates that already-open tab once the URL is ready — no new pop-up, so nothing gets blocked. Mobile has no such restriction, so reserveLaunch() does nothing there — call it anyway so the same code runs unchanged on both platforms.

Handling the return

Four outcomes, and only one of them says anything about a payment — and even then only provisionally.

OutcomeMeans
ZpReturnReceivedThe device came back to your app. Read t off the return URI and ask your backend for the real status. Nothing more than that.
ZpPresentationDismissedClosed before returning. Dismissal is not cancellation — it may still have completed server-side, so do not report it as cancelled.
ZpTimedOutNo return arrived within the configured timeout (10 minutes by default).
ZpLaunchFailedPresentation never started; ZpLaunchFailureCode says why.

Mobile

The return arrives as an App Link / Universal Link via app_links. There is no native dismissal callback on Android, so dismissal is inferred from app-resume plus a 500 ms grace period — letting an incoming deep link win the race. Seeing ZpPresentationDismissed just before a return is that mechanism working.

Web

Checkout opens in a second tab, so that tab must relay the return back to the opener. Call completeWebCheckoutReturnIfPopup(expectedReturnUri: ...) as the first line of main() and return immediately when it reports true — that window is the popup and has nothing to render.

A return is not a payment

Show a green tick on ZpReturnReceived alone and the app reports "paid" for a customer who abandoned checkout and pressed back. Success UI must come from a backend status lookup whose verified-callback flag is true.

Telemetry is opt-in through ZpCheckoutObserver: the SDK logs nothing by default, emitted events omit tokens and full checkout URLs, and exceptions thrown by an observer are caught and discarded so observability can never alter checkout.

The CheckoutPresenter contract

One abstract contract with one job: openCheckout(url, ...) → PresentationLaunchResult. zenpay_flutter ships the default implementation — Android Custom Tabs, iOS SFSafariViewController, a new browser tab on web. zenpay_embedded is a second implementation of the same contract, and section 3 is entirely about what that swap costs.

dart · the entire swap
final checkout = ZpCheckout(
  configuration: configuration,
  returnUriSource: presenter.returnUriSource, // only differs when embedding
  presenter: presenter,                        // <- this is the entire swap
);

Nothing about ZpCheckoutConfiguration, ZpCheckoutOutcome, launch URL validation or return URI validation changes.

03Optional presenter · never the default

zenpay_embedded

An in-app modal WebView presenter for merchants who need checkout to stay inside the app. It adds one implementation of CheckoutPresenter and changes nothing else. Its barrel exports only EmbeddedCheckoutPresenter — the WebView widget, the navigation policy and the return source all stay internal, so there is no widget for a merchant to place in their own tree.

What actually changes

PCI DSS SAQ A

Eligibility disclaimer, verbatim

This document does not determine SAQ eligibility for anyone. It describes what each presentation surface does and enforces. Actual SAQ eligibility depends on the merchant's complete environment, payment integration, provider status, and acquirer/payment-brand rules, and must be confirmed with the merchant's own acquirer and/or QSA (Qualified Security Assessor).

There is no WebView object for the app to hold. Android Custom Tabs and iOS SFSafariViewController render the hosted page inside the operating system's own browser process (Chrome / Safari) — a fully separate process from the app's. The app never has a handle to that page's document, its JavaScript context, or its navigation. Every risk in § 3 below (a JavaScript bridge, a caller-controlled navigation delegate, a sub-frame sharing a document with merchant script) requires a WebView object to exist in the first place. Here, none does — the risk isn't mitigated, it's structurally absent.

PCI_SAQ_A.md § 1

That is why the system browser is the default rather than merely the first surface shipped. The entire payment journey — card entry, any 3DS challenge, wallet buttons — happens inside ZenPay's hosted page; your app never renders a step of it and never sees the data. A full browser runs that page with no capability restrictions, so the default surface needs no manifest entries or feature flags to support any of it. An embedded WebView is a reduced-capability environment by comparison, which is where the extra requirements below come from.

The five controls this package enforces

§Mistake it preventsWhat the package does instead
3.1Adding a JavaScript bridgeNever calls addJavaScriptChannel or setOnConsoleMessage. On iOS the handler registers at the WKWebViewConfiguration level regardless of frame-scoping — reachable from every frame, including third-party 3DS/ACS frames. There is no safe way to add one.
3.2Accepting a caller-supplied WebViewControllerThe widget builds its own and accepts none — structurally, not by convention. A supplied controller could carry a bridge the grep gate cannot see.
3.3Allowlisting navigation by hostRestricts navigation to https only, never a host allowlist. A 3DS challenge sends the customer to their own issuer's ACS host, which cannot be enumerated in advance.
3.4Embedding checkout as a sub-frameOnly ever performs full top-level navigation. Merchant script sharing one document with the PSP's frame is the pattern that typically moves an integration from SAQ A to the heavier SAQ A-EP.
3.5Leaving browsing state behindOn dismiss, navigates to about:blank, then clears cache, local storage and cookies in that order. webview_flutter exposes no per-instance store, so leftovers are reachable by any other WebView in the app.

Google Pay is a host-app requirement, not a control — verified by a live device test

PCI_SAQ_A.md § 3.6 is explicit that this is a platform restriction rather than a PCI control. The package opts in to the WebView's Payment Request API via AndroidWebViewController's native WebViewFeatureType.paymentRequest flag — a WebSettings-level toggle, not a JavaScript channel, so it carries none of the § 3.1 bridge risk. Tested on a real device (Pixel 9 Pro XL, embedded-WebView demo, 2026-08-25): commenting out _enableGooglePayPaymentRequest() and rebuilding reproduces Google's own in-page failure verbatim — "Something went wrong. Google Pay couldn't load properly because this App uses a WebView. App developers must follow the instructions to enable Google Pay to work within Android WebView: https://goo.gle/gpay-android-webview-help [OR_BIBED_15] OR_BIBED_15". With the flag restored, Google Pay has worked across every checkout mode in extensive real-device testing.

You do not need to add <queries> entries (org.chromium.intent.action.PAY, IS_READY_TO_PAY, UPDATE_PAYMENT_DETAILS) to AndroidManifest.xml for this to work — the example app declares only the PROCESS_TEXT query flutter create generates, and Google Pay still works reliably as-is. This package ships no native android/ folder of its own, so if your own target devices ever do need manifest changes, that's a per-merchant integration step, not something this package can auto-merge.

Three controls have commit-time regression guards

GuardFails the commit when
no-js-bridgeaddJavaScriptChannel or setOnConsoleMessage appears anywhere in zenpay_embedded/lib.
webview-teardownThe WebView widget stops calling clearCache, clearLocalStorage, or WebViewCookieManager.
webview-no-host-allowlistThe navigation policy ever references isAllowedCheckoutUrl or allowedCheckoutHosts.

§ 3.2 and § 3.4 are structural rather than forbidden-pattern checks — there is no parameter to pass a controller through, and full-navigation-only is a single call site — so a reviewer reading the diff is the check there.

Outstanding gates are process, not code

Still required before embedded mode can be advertised as SAQ-A-compatible: ZenPay product approval, 3DS certification, a tested wallet matrix, external-app switching tests, cookie and storage tests on physical devices, accessibility testing, and QSA review. No code change closes any of these. SAQ A merchants may also still carry ASV scanning responsibilities for their own web pages.

Setup checklist

Ordered by what each step writes and the next step reads. Your progress is saved in this browser.

  1. any terminal

    Clone and bootstrap

    One command does the whole first-run setup. It refuses to continue without flutter and dart on PATH.

    shell
    $ git clone https://github.com/zenith-payments/zp-flutter-sdk
$ cd zp-flutter-sdk
$ dart run cli.dart --bootstrap

    In order, --bootstrap resolves the pub workspace with dart pub get; copies both .env files from their .example templates only if they do not already exist; prompts for the values the backend refuses to start without; generates the mkcert TLS cert; and writes assetlinks.json for your machine.

    Blocks

    Nothing downstream works without it — the workspace is unresolved, so dart run fails in every package.

  2. same prompt

    Answer the prompts

    Four ZenPay credentials plus one local secret, asked one at a time. Enter keeps whatever is already set.

    PromptKindWhat to enter
    ZENPAY_MERCHANT_CODEpublicFrom your ZenPay sandbox or production merchant account. Not included in this repo.
    ZENPAY_API_KEYpublic
    ZENPAY_USERNAMEprivateNever leaves the backend — both are hash inputs for the fingerprint and the callback ValidationCode.
    ZENPAY_PASSWORDprivate
    TOKEN_SECRETlocalNot a ZenPay credential — it is this backend's own root signing secret. Leave blank and one is generated for you, 32 secure random bytes as hex.
    Blocks

    Missing any of these and bin/server.dart's main() refuses to start at all — it exit(1)s immediately with the exact missing keys listed on stderr, rather than serving and failing deeper in. (The 503 SESSION_CONFIGURATION_REQUIRED response in server_app.dart is a second, defense-in-depth check on the same values — in practice you see the startup refusal first.)

  3. terminal 1 — leave running

    Start a public tunnel

    Before the server, because the server prompt asks for the URL this prints.

    terminal 1
    $ dart run cli.dart --quick-tunnel

    Runs cloudflared tunnel --url http://localhost:<PORT>, reading PORT from the backend .env and falling back to :7000. No Cloudflare account needed. For a stable URL across restarts use --tunnel, which prompts for a durable token and saves it.

    Partly optional

    Skip it and checkout still launches — you reach ZenPay's hosted page. What breaks is everything after: the callback is server-to-server and cannot reach localhost, so no payment is ever confirmed. On Android it also breaks the return trip, because App Link verification needs a publicly fetchable host.

  4. terminal 2 — leave running

    Start the backend

    The only step that prompts for the tunnel URL and re-syncs native Android/iOS config from it — must run before step 5, not after.

    terminal 2
    $ dart run cli.dart --server

    Runs on :7000. Prompts for PUBLIC_BASE_URL — paste the tunnel URL step 3 printed — and, on any value (including keeping the existing one), derives APP_RETURN_URI_MOBILE into example/app/.env and re-syncs AndroidManifest.xml/Runner.entitlements to match. Needs no service-account.json: reCAPTCHA is optional here, disabled when the three RECAPTCHA_* variables are empty.

    Blocks

    Keep PUBLIC_BASE_URL at localhost (Enter through the prompt with no tunnel running, or --keep-url before one exists) and checkout still launches, but ZenPay's callback can never reach you and the Android App Link never verifies against a host nothing can fetch /.well-known/ from.

    Running it in Docker instead

    dart run cli.dart --docker-run runs the backend and the web frontend in containers on :7000/:8080 from docker/local/docker-compose.yml, plus the tunnel when a token is configured — always through cli.dart, never docker compose directly, since the Compose build context only resolves the way cli.dart invokes it. It does not prompt for PUBLIC_BASE_URL (set it in example/backend/.env yourself first) and does not re-sync native Android/iOS config — only --server and --android do that. It refuses to start unless example/backend/.env exists, and generates the mkcert cert pair in example/app/ itself if mkcert is installed and one isn't already there. The backend service also bind-mounts example/backend/service-account.json — Compose has no way to make a bind mount optional, so cli.dart auto-creates an empty placeholder there if you don't have a real one, rather than refusing to start. reCAPTCHA is still fully .env-driven, same as native: leave all three RECAPTCHA_* vars empty and it stays off (the empty placeholder is never read); set them and put your real GCP key at example/backend/service-account.json on the host for it to resolve through the mount. It cannot run the Android/iOS app itself, so step 5 still runs on your host either way. Use --docker-rebuild when the image looks stale, --docker-build alone to build without running.

  5. terminal 3

    Run the app

    Each mode re-syncs native config first, then hands off to flutter run.

    terminal 3
    $ dart run cli.dart --android          # adb reverse tcp:7000, then flutter run
$ dart run cli.dart --android-webview  # the zenpay_embedded WebView demo
$ dart run cli.dart --ios              # macOS only
$ dart run cli.dart --web              # Chrome on https://localhost:3000
    • Android sets up adb reverse tcp:7000 tcp:7000 so the device reaches the backend on your host's localhost, auto-picking the device (or pass --device=<id>). --android re-syncs the native manifest itself before every run (cli.dart's _android calls the same _syncNativeAppLinkConfig step 4 did), so the install always re-verifies against whatever host is currently in example/backend/.env — never a stale one from an earlier run.
    • Web serves on localhost:3000 over TLS with the mkcert cert, matching APP_RETURN_URI_WEB. Without the cert it runs over plain HTTP and warns — but the HTTPS return URI will not match.
    • iOS has no adb reverse equivalent: the simulator shares the host's localhost, and a physical device needs the backend on the LAN or behind the tunnel.
    Blocks

    Run this before step 4 and the app is built against whatever host the manifest last held. On Android the return then opens a browser tab instead of your app, and checkout appears to hang until it times out.

  6. on device

    Confirm the launch works

    The app opens on a transaction-mode picker: Make Payment, Tokenise, Custom Payment, Preauthorization.

    Fill in the form and tap Pay. Landing on ZenPay's hosted sandbox checkout page confirms steps 1–5 are wired correctly. To see the full round trip — checkout completing and the app receiving a verified result — the tunnel from step 3 must be live.

    Diagnostic

    If checkout launches but the app never hears back on Android, the App Link did not verify. Confirm PUBLIC_BASE_URL is the tunnel host, that assetlinks.json exists, and reinstall so Android re-runs verification.

  7. any terminal

    Run the verification suite

    Confirm the checkout is green on a clean tree before you change anything.

    repository root
    $ melos bs
$ melos run format
$ melos run analyze
$ melos run test
$ melos run test:dart
$ dart run scripts/check_claude_md.dart
    Enforced anyway

    The lefthook pre-commit gate runs format, analyze, analyze-root, test, and the three WebView regression guards (no-js-bridge, webview-teardown, webview-no-host-allowlist) — seven checks, no lint step; this repo declares no lint package. GitHub Actions then re-runs formatting and analysis on every pull request, followed by a test matrix across all five packages (.github/workflows/pr_check.yaml) — so running these locally first just saves a rejected commit and a red PR.

  8. reading

    Internalise the trust model

    One rule outranks everything else, and getting it wrong looks completely correct.

    Only the signed callback decides

    Every ZpCheckoutOutcome is provisional — it means the customer's device came back. Only verifyZpCallback's constant-time ValidationCode check establishes that money moved. See section 1 for the call and section 2 for the outcomes.

05Dev launcher

cli.dart

One cross-platform launcher at the repo root, replacing what would otherwise be a per-platform pile of shell scripts. Every mode runs as a live, attached process — Ctrl+C stops it, logs stream to your terminal, nothing runs detached. Exactly one mode flag per invocation.

Verification

Run from the repository root. These are the same gates the pre-commit hook enforces, and both CI pipelines re-run on every push and pull request: GitHub Actions (.github/workflows/pr_check.yaml) re-runs formatting, analysis and the full test matrix; Codemagic (codemagic.yaml) runs the same checks plus Android/iOS/Web debug builds.

repository root
$ melos bs           # resolve the workspace — never `pub get` in a subdirectory
$ melos run format
$ melos run analyze
$ melos run test      # flutter test, Flutter packages with a test/ dir
$ melos run test:dart # dart test, pure-Dart packages with a test/ dir
$ dart run scripts/check_claude_md.dart

No melos run lint — this repo declares no separate lint package (dart_code_linter, very_good_analysis) anywhere; strictness comes entirely from analyze plus each package's analysis_options.yaml. The last command checks every CLAUDE.md against scripts/claude_md_template.md — required sections in order, plus a dedicated entry for every source file. There are nine, one per package plus the root.

repository root
$ dart run cli.dart --check

Runs all of the above in one shot, across the whole tree — not just staged files, unlike the pre-commit hook's format/analyze-root gates. A failing step reprints its own output under a final "Why" section so you don't have to scroll back for it.
