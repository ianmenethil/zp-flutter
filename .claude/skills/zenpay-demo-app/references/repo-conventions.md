# Repo conventions

What this monorepo enforces on any package added to it. The scaffold handles most of it; this
is here for when something fails and the message is not obvious.

---

## The pub workspace

This repo is a Dart pub workspace, with Melos driving multi-package scripts on top of it.
Two consequences that break a new package immediately:

1. **Every member declares `resolution: workspace`** in its own `pubspec.yaml`, and sibling
   SDKs are referenced by ordinary version constraint (`zenpay_dart: ^0.1.0`), never a
   `path:` dependency. A `path:` dep is *rejected* once a package is a workspace member — the
   workspace already provides that link.
2. **The root `pubspec.yaml`'s `workspace:` list is explicit, not globbed.** A new package
   must be added to it by hand (the scaffold does this). Forgetting produces a resolution
   error that names the package but not the reason.

Melos's own `packages:` list *is* globbed — `example/*` — but it matches **direct children
only**. `example/coffee_backend` is picked up; `example/coffee/backend` is not. Generated
packages are therefore flat: `example/<name>_backend`, `example/<name>_app`.

Run `melos bs` from the root after scaffolding. Never `dart pub get` or `flutter pub get`
inside a subdirectory.

**The published packages are not on pub.dev yet** (per `scripts/CLAUDE.md`, the committed
version constraints cannot resolve before a first real publish). This is exactly why demos
live inside the workspace: outside it, they would need `pubspec_overrides.yaml` path
overrides to resolve at all.

## Do not touch the generated example copies

`zenpay_dart/example/` and `zenpay_flutter/example/` are gitignored copies of
`example/backend` and `example/app`, regenerated by `dart run cli.dart --sync-examples`.
Never hand-edit them. `sync_package_examples.dart` only syncs those two specific sources, so
a new `example/<name>_*` package is not swept into them — that is fine and intended.

## Analysis strictness

`strict-casts`, `strict-inference`, `strict-raw-types` across every package. No `dynamic`.
`final` locals. Constructors sorted first. 160-character page width. Unused imports, private
members, and locals are **errors**, not warnings — clean them rather than suppressing them.

Every exported symbol in `lib/` needs a doc comment explaining purpose and failure modes.
This is convention, not lint-enforced (`public_member_api_docs` is off package-wide, because
primary-constructor syntax gives a class no line for a constructor doc to attach to).

## Generated demos ship no tests

Deliberate. A demo is an illustration, not a library — its job is to be read and run, and
test scaffolding is noise between the reader and the integration. `lefthook`'s test gate
filters on `dirExists: test`, so a package without a `test/` directory is skipped rather than
failed, and a `--committed` demo commits cleanly with none.

If a demo ever grows something genuinely worth guarding, the one test to write first is that
a callback with a forged `ValidationCode` is rejected — everything else in a demo is
cosmetic, that one is the trust model.

## The CLAUDE.md contract

Only relevant with `--committed`. Any folder with its own `CLAUDE.md` is checked by
`dart run scripts/check_claude_md.dart` against `scripts/claude_md_template.md`:

- a top-level `# ` title;
- `## Related Guides` then `## Verification`, in that order (a numbered or extended heading
  like `## 3. Verification Commands` also satisfies it);
- **every** file matching `lib/**/*.dart`, `bin/**/*.dart`, or `*.dart` must appear as a
  dedicated heading or bullet entry — a mention inside prose does not count.

The standing repo rule: changing a file in a folder that has a `CLAUDE.md` means updating
that `CLAUDE.md` in the same diff. A generated package that ships one must keep it accurate
as its source grows, or the check fails on the next commit.

## Commit gates

`lefthook` pre-commit runs: `format`, `analyze`, `analyze-root`, `lint`, `test`,
`no-js-bridge`, `webview-teardown`, `webview-no-host-allowlist`. CI is currently disabled
(`.github/workflows/pr_check.yaml.bak` is not a live workflow), so this hook is the only
enforcement. The last three only bite `zenpay_embedded`, which a demo should not be touching.

Verify before committing:

```bash
melos run format
melos run analyze
melos run lint
melos run test
dart run scripts/check_claude_md.dart
```

## Running things

Use `cli.dart`, not raw `flutter run` — it handles `.env` prompting, `adb reverse`, TLS certs
for the web return flow, and re-syncing native App Link config when `PUBLIC_BASE_URL` changes.
`dart run cli.dart --help` lists every mode.

A generated demo backend must not collide with `example/backend` on `:7000`. The scaffold
picks a free port and writes it into both `.env` files and the run command.

## Searching this repo

Plain `grep` through Bash ignores `.gitignore`; the Grep tool and VS Code search respect it.
That difference matters here — `zenpay_dart/example/`, `zenpay_flutter/example/`, and `.bak/`
are all ignored copies of real source. A `grep` hit in one of those is not evidence the thing
exists in the live tree. Cross-check before concluding anything is or is not in the repo.
